None Is Not an Error

by Jeff Thoensen

The lookup used to fail without ever raising anything. If the MLB API had no player matching a name, search_player_id printed "Player not found." and returned None, and the caller was responsible for noticing the None and stopping. Forget that check anywhere in the chain, and None keeps traveling into the next function that expected a real player ID.

Testing that old version meant capturing whatever got printed to stdout and asserting on the message, then separately checking that the return value was None. Replacing the print-and-return-None pattern with a real exception, PlayerLookupError, meant one assertion covers it: pytest.raises(PlayerLookupError) either happens or it doesn't, with nothing else to check.

The exception also fixed a case the print statement couldn't. The function that decides between pitching and hitting stats used to return (None, None) when a player had a season with no usable stats, the same shape the caller was already checking for a missing player entirely, so both very different problems ended up as the same "something is None, give up" check. Raising PlayerLookupError with an actual message, "No usable stats available for 2025" versus "No player found matching...", means the two failures look different from the moment they happen, instead of only being distinguishable by whichever print statement ran first.

Adding argparse alongside the exceptions mattered for a related reason. Running the script with a name as an argument, instead of only through the interactive prompt, meant tests could call the lookup function directly with a name and a mocked response, instead of needing to fake stdin to drive the interactive version.
